Gate A's persistent Namespace `.lake` cache volume (ADR-046) is now observable and reclaimable, so it stops silently filling to its cap and ENOSPCing `lake exe cache get` on cold mathlib decompression — the failure that sinks an ADR-107 batch run (a `replay` shard that lands cold on a full 50 GB volume dies with "No space left on device"). Two parts: (1) Gate A's `.lake` cache diagnostics now print `df -h` **and** `df -i` — capacity in bytes *and* inodes, since mathlib olean trees are millions of tiny files and the volume can exhaust inodes while bytes look free; (2) a new `lake-volume-janitor` workflow + `tools.repo.lake_volume` survey the volume (capacity, `du` composition, live toolchain pins, reclaimable candidates) **report-only by default**, with a manual `--apply` that conservatively reclaims decompressed-then-redundant `mathlib-cache/*.ltar` archives and gc's loose git objects — never a live pin's oleans. `--apply` is gated behind an operator dispatch because the volume is shared with in-flight Gate A runs.
